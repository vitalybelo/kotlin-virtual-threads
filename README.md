# Kotlin Virtual Threads Demo
Этот проект kotlin-virtual-threads представляет собой практическую демонстрацию работы виртуальных потоков (Virtual Threads) в Spring Boot приложении на языке Kotlin. Главная цель демо — показать, как виртуальные потоки позволяют колоссально увеличить пропускную способность веб-сервера при выполнении долгих блокирующих операций (I/O, сетевые запросы), избегая при этом блокировки ценных платформенных потоков операционной системы.   

Чтобы результаты были максимально наглядными, в файле application.yaml искусственно создано «узкое горлышко»: пул потоков встроенного сервера Tomcat жестко ограничен всего 10 потоками (server.tomcat.threads.max: 10).   
```yaml
server:
  tomcat:
    threads:
      max: 10
```   

Проект демонстрирует два принципиально разных подхода к интеграции виртуальных потоков, которые переключаются через свойство spring.threads.virtual.enabled.   

## 1. Глобальный режим (Global Virtual Threads)

Как включить: Установить spring.threads.virtual.enabled: true в application.yaml.
```yaml
spring:
  threads:
    virtual:
      enabled: true
```   
В этом режиме класс ThreadConfig переопределяет стандартные настройки Tomcat и AsyncTaskExecutor, переводя весь веб-сервер на использование виртуальных потоков (Executors.newVirtualThreadPerTaskExecutor()).   

Endpoint:
 
GET http://localhost:8080/virtual-threads/enabled/demo

Логика: Метод контроллера VirtualThreadController работает полностью синхронно. Он вызывает Thread.sleep(1000L) и возвращает строку с именем потока.   

Поведение: Tomcat не использует свой пул из 10 потоков. Для каждого входящего HTTP-запроса создается новый одноразовый виртуальный поток, который засыпает на 1 секунду. Платформенные потоки ОС остаются свободными.

## 2. Гибридный режим (Tomcat Platform Threads + @Async Virtual Threads)
   
Как включить: Установить spring.threads.virtual.enabled: false   
```yaml
spring:
  threads:
    virtual:
      enabled: false
```   

Глобальные виртуальные потоки отключены, и Tomcat обрабатывает запросы своими 10 платформенными потоками. При этом класс AsyncConfig создает отдельный пул asyncVirtualExecutor на базе виртуальных потоков специально для асинхронных задач.   

Эндпоинт:

GET http://localhost:8080/virtual-threads/disabled/demo

Логика: Контроллер HybridController принимает запрос. Он логирует имя платформенного потока Tomcat и вызывает метод fetchExternalData() из IntegrationService.   

Делегирование: Метод в сервисе помечен аннотацией @Async("asyncVirtualExecutor") и возвращает CompletableFuture. Он симулирует долгий сетевой вызов через Thread.sleep(1000L).   

Поведение: Платформенный поток Tomcat (один из десяти) принимает запрос, мгновенно делегирует тяжелую задачу в виртуальный поток и сразу возвращается в пул, готовый обслужить следующего клиента. Физически 1-секундную паузу отрабатывает виртуальный поток.   

## 3. Нагрузочное тестирование
В корне проекта находится исполняемый файл LoadTester.kt — консольный генератор нагрузки. Алгоритм работы:

1. Отправляет 1000 HTTP-запросов к выбранному эндпоинту (по умолчанию к /virtual-threads/disabled/demo).   
2. Запускает каждый запрос в отдельном виртуальном потоке через Executors.newVirtualThreadPerTaskExecutor().   
3. Использует «плавный старт» (Ramp-up): перед отправкой запроса поток делает паузу Thread.sleep(1L). Это размазывает отправку 1000 запросов ровно на 1 секунду, предотвращая ошибку ConnectException из-за переполнения очереди соединений на уровне ОС.   
4. Подсчитывает успешные ответы с помощью AtomicInteger и замеряет общее время выполнения теста через measureTimeMillis.

### Анализ результатов тестирования
При запуске LoadTester.kt на эндпоинте гибридного режима (/disabled/demo) происходит следующее:   

**Время выполнения**: Итоговое время выполнения теста из 1000 запросов составит около 1.5 - 2 секунд (зависит от мощности машины).

**Математика успеха**: Если бы контроллер обрабатывал 1-секундный sleep на пуле из 10 платформенных потоков Tomcat без CompletableFuture и @Async, сервер мог бы переваривать только 10 запросов в секунду. Тест выполнялся бы ровно 100 секунд.

**Логирование**: В консоли сервера будет видно, что запросы принимаются потоками Tomcat (вывод из HybridController), но сама успешная отработка и 1-секундное ожидание выполняются внутри потоков VirtualThread[#...] (вывод из IntegrationService).   

Оба режима (Глобальный и Гибридный) успешно решают проблему масштабирования долгих I/O операций, позволяя обрабатывать тысячи конкурентных подключений при минимальных лимитах аппаратных потоков ОС. Гибридный режим с @Async особенно полезен в реальных проектах, где требуется защитить пул соединений с БД (HikariCP) платформенными ограничениями Tomcat, но при этом дать бесконечную масштабируемость сторонним сетевым интеграциям.
